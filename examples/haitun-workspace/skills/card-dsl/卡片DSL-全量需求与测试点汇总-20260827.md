## 第一部分 · 背景与总目标（需求源头）

- 【需求】公司海豚集成于飞书，所有管理 SOP 的人机交互最终落在飞书交互式卡片上。
- 【需求-痛点】现状每类卡片（评价卡、todo 卡、报表卡）都手写飞书卡片 JSON，每做一个新卡都要重新应对飞书协议限制，成本高、体验打磨慢。
- 【需求-总目标】定义一层**卡片通用元素 DSL**（XML 形式），业务只声明"卡上有什么"（标题、负责人、打分、评语、按钮），由**渲染引擎**编译成飞书卡片 JSON 并统一处理飞书协议限制。
- 【需求-验证目标】验证"业务写 DSL、引擎消化复杂度"这条路可行，为后续其他通用元素（表格、文档、任务）树立范式。
- 【设计-三层形态】XML DSL（原创语言）→ 渲染引擎（原创编译器）→ 飞书卡片 JSON（渲染后端）。
- 【设计-DSL 剥离】DSL 层已完全剥离飞书概念，业务不出现任何飞书 JSON。
- 【设计-后端定位】渲染后端必须基于飞书卡片，这是产品定位决定的（海豚集成在飞书，飞书内唯一能承载按钮/输入框/勾选的载体就是飞书卡片），不是技术限制。
- 【设计-可替换架构】引擎内部按"DSL → 后端适配器"组织，当前唯一后端是飞书卡片；将来出网页版/独立客户端时新增 HTML 渲染后端即可，DSL 与引擎核心不动。本实验不做第二个后端，只保证架构预留。

### 为什么要定义这层 DSL（而非业务直接写飞书 JSON）
- 【设计】飞书 JSON 太啰嗦：业务真正关心的只有十几个词，飞书卡片 JSON 却要几百行协议细节，90% 与业务无关。
- 【设计】坑要业务自己扛：按钮一次性消费、input 值回传、组件限制，每次写卡都要重新绕。
- 【设计】机器生成不可靠：LLM 直接生成几百行嵌套 JSON 出错率高；DSL 把生成对象简化到十几行声明，出错率大幅下降。
- 【设计-一句话】把 90% 协议细节从业务手里拿走，业务只写关心的 10%。

### 为什么用 XML 而非 JSON
- 【设计】必须和飞书 JSON 区分：飞书卡片协议本身就是 JSON，DSL 再用 JSON 就是"JSON 套 JSON"，人和 LLM 都容易混，嵌套嵌入还要层层转义；XML 与 JSON 视觉差异极大，一眼分清。
- 【设计】XML 适合写声明：属性写法（`type="reject"`）天生表达"元素+属性"的声明式内容。
- 【设计】XML 可读、可注释：像 HTML 一样层级清晰，非技术同事也能看懂；支持 `<!-- -->` 就地注释。JSON 官方不支持注释。
- 【设计】LLM 生成 XML 更稳：训练语料里 HTML/XML 海量，生成十几行 XML 出错率远低于几百行嵌套 JSON。

### 三层正交定位（本方案只做第一层）
- 【设计】① 卡片设计层（DSL）——定义"一张卡可以长什么样"，静态零件。
- 【设计】② 卡片使用层（业务）——决定"发给谁、点按钮后发生什么"。
- 【设计】③ 触发层——定时/事件/对话决定"什么时候用"。
- 【设计】todo 卡、评价卡是第②③层的实例，是 DSL 的第一个用户。

## 第二部分 · 范围界定

- 【要求-只做卡片】本实验不涉及表格、文档、任务等其他元素。
- 【要求-素材来源】以已完成的三类卡片（评价卡、todo 卡、报表卡）为抽象样本，其中评价卡最复杂（打分、评语、打回、多轮操作），作为 DSL 能力的主要标尺。
- 【要求-不动业务逻辑】打分落账、评语写台账等业务动作保持现有直调工具不变，本实验只替换"卡片的生成方式"。

## 第三部分 · DSL 设计需求（词汇表、三层结构、语义颜色）

### 3.1 词汇表（8 个元素）
- 【设计】词汇表是**开放的积木盒**：第一版收录三类已验证卡型抽象出的块，按场景组装、按需增长；未来新 SOP 需要新交互时扩充词汇表，引擎同步支持。

| 元素 | 干什么 | 可交互 | 关键属性/示例 |
|---|---|---|---|
| `card` | 根容器，定标题和卡头配色 | 否 | `title`、`template`（如 `<card title="TODO 评价" template="blue">`） |
| `info` | 一行信息"标签:值"，纯展示 | 否 | `label`、`value`、`bind-record`（如 `<info label="执行人" value="黄子建"/>`） |
| `score` | 打分按钮组，能多轮改分 | 是 | `min`、`max`、`rounds`、`bind-record`、`selected`（如 `<score min="1" max="5" bind-record="recX"/>`） |
| `comment` | 评语输入框（引擎自动配"确认"按钮） | 是 | `placeholder`、`bind-record` |
| `action-row` | 按钮行容器（布局块） | —— | 容纳 `button` |
| `button` | 一个动作按钮（最小交互单元） | 是 | `text`、`type`、`action`（如 `<button text="打回重做" type="reject" action="review_reject"/>`） |
| `list` | 待办列表（todo 卡） | —— | 容纳 `row` |
| `row` | 列表里的一行待办 | 是 | `title`、`done`（如 `<row title="写方案" done="true"/>`） |

- 【设计-层级】`card` 层级最高是容器（自己不含内容，只负责容纳）；`info`/`score`/`comment` 是功能块；`action-row` 是布局块；`button` 是最小单元，通常装在 action-row 里。

### 3.2 元素 / 属性 / 映射：三层结构
- 【设计-第一层 元素】"是什么"。`button` = 按钮。
- 【设计-第二层 属性】"什么语义"。`type="reject"`（这是驳回）。
- 【设计-第三层 映射】"语义落地为飞书样式"。引擎映射表把 `reject` 翻译成飞书按钮红色样式。
- 【要求-业务只写语义不写颜色】比如按钮写 `type="reject"` 引擎自动映射成红色；`type="accept"` 自动映射成蓝色。换配色只改引擎里一张映射表，业务代码一行不动。

### 3.3 语义颜色映射表（开发者维护）
- 【设计】`reject` → `danger`（红）；`accept` → `primary`（蓝，见下）；`danger` → 红；`default` → 灰；`primary` → 蓝。
- 【设计】卡头模板：`blue` → header_template blue；`green` → green；`red`、`grey` 同理。
- 【设计-飞书限制】飞书按钮只有灰(default)/蓝(primary)/红(danger)三色，绿色按钮做不出来——`accept → 绿色`是设计意图，映射表先落到最近可用样式（蓝），飞书开放后改映射表一行即可。
- 【设计】卡头模板色（blue/green/red/grey）飞书原生支持，映射完整。

### 3.4 Action 六环（多轮交互机制）—— 最精巧的一环
- 【设计-1 声明】XML 里只写两个回调相关词：`action`（这个按钮干什么）和 `bind-record`（关联哪条记录），不写任何飞书回调概念。
- 【设计-2 生成带轮次动作名】引擎把动作名改写成 `{动作}_r{轮次}`（如 `review_score_r0`、`review_score_r1`），轮次从 0 起、上限 20。
- 【设计-3 预注册映射】引擎一次性把全部 20 轮都注册到对应处理工具（点分→feishu_review_card_select、评语→feishu_review_input、打回→feishu_review_reject），哪一轮点都有人接。
- 【设计-4 回调值组装与反解】按钮被点时回传数据自动带 `record_id`（来自 bind-record）+ 业务字段 + 动作名 + 轮次 +（打分还带分数）；收到回调后按同一套字段契约反解出"谁、对哪条记录、第几轮、做了什么"。字段只定义一次。
- 【设计-5 状态重建】改 `selected`（高亮选中分数，单选互斥）+ 轮次号 +1，用同一份模板重新渲染，原位更新卡片：分数高亮、评语回填、`已打分`状态行更新。重建由处理方（直调工具）调引擎完成，秒级原位覆盖飞书"已提交"过渡。
- 【设计-6 业务边界】回调的业务动作（打分落账、评语写台账）仍由现有直调工具执行，引擎只负责"把回调路由到工具"和"重建卡片"，不掺业务逻辑——这是引擎与业务的分界线。
- 【设计-一句话】飞书按钮是一次性的，引擎靠"每次操作换一批全新按钮名"伪装成可反复点。

## 第四部分 · 渲染引擎职责

### 4.1 编译职责
- 【需求】解析 XML 声明，编译成飞书卡片 2.0 JSON（业务不出现任何飞书 JSON 概念）。
- 【需求】自动应用语义颜色映射表（template/type → 飞书实际样式字段）。
- 【需求】自动为 input 类元素附加 confirm（飞书输入值唯一回传通道）。
- 【设计】引擎支持编译成飞书 2.0 / legacy 两种卡（见第一版总结）。

### 4.2 引擎返回
- 【要求】引擎返回 `{ok, card, handlers}`（校验合法 → 编译 → 产出 card + 动作映射表）。

### 4.3 飞书限制处理清单（固化进引擎，业务不可见）
- 【要求】按钮一次性消费 → `rounds` 参数（每次重建轮次 +1 生成全新 action）。
- 【要求】input 值仅 confirm 可回传 → 引擎自动加 confirm 按钮。
- 【要求】textarea / form_container / button_group 不支持 → 词汇表设计时直接规避。
- 【要求】点击后"已提交"过渡 → 原位重建秒级覆盖。

### 4.4 数据库预留（Dustin 第 4 点的落地）
- 【要求】引擎入口只吃一个 XML 字符串参数（`render_card` 吃 `card_xml`），引擎不关心 XML 从哪来。
- 【设计】现在：模板文件 read → XML 字符串 → render_card → 飞书卡。将来：数据库查 → XML 字符串 → render_card → 飞书卡。切换时只替换"读文件"那一步，引擎核心、模板、业务调用零改动。

### 4.5 既有机制复用
- 【设计】现有 `send_card_impl` / 快照 / `edit_card_impl` / 直调分发是引擎雏形，引擎在其上新增"DSL 编译 + Action 生命周期管理"两层，不重写现有机制。

### 4.6 模板机制
- 【设计】两个固定卡型模板：`templates/review-card.xml`（评价卡）、`templates/todo-card.xml`（todo 卡）——发卡时只填数据不写结构。
- 【设计-为什么做模板】固定卡型形态已定型；把 XML 交给 LLM 每次现场自由发挥会拼错标签/属性、发卡失败、出错率不可控。模板化后 LLM 只填数据、不写结构（结构锁死在模板），占位符 `{key}` 填充时自动做 XML 转义。
- 【用法-三种】① 固定卡型用模板（`render_template("review-card", session={...})`，只填数据不碰结构）；② 新卡型手写 10 行 XML 传 `card_xml=...`。

## 第五部分 · 实施步骤与倒排（含 DDL）

1. 【步骤-8.24~8.25】盘点与规范：拆解三类已有卡结构，输出《卡片 DSL 词汇表与字段规范》——以 XML Schema (XSD) 形式交付并带注释（海豚将来按此 Schema 生成 XML、解析器按此做合法性校验），含飞书限制处理清单与语义颜色映射表。
2. 【步骤-8.25~8.26】渲染引擎骨架：DSL 解析器 + 按 XSD 做 XML 合法性校验 + 飞书 JSON 编译器；同时预留"卡片定义加载"接口（本期从代码/文件读 XML，将来可切换数据库读取，核心编译逻辑不受影响）。
3. 【步骤-8.26~8.27】引擎进阶能力：Action 统一处理六环实现——动作声明解析、带轮次动作名生成、handlers 自动映射、回调 value 组装与反解、状态重建（分数高亮/评语回填/轮次+1）、引擎与业务边界隔离。
4. 【步骤-8.27~8.28】业务验证：评价卡改用 DSL 生成，飞书实卡交互与原版完全一致（点分/评语/打回/多轮）。
5. 【步骤-8.27~8.28】通用性验证：再取一个卡型（报表卡或新设计一个审批卡）用 DSL 写出，引擎零改动。

## 第七部分 · Dustin 评审意见（4 条）

1. 【要求】DSL 语法为 XML Schema 形式并带注释；最终用户可以将此 Schema 扔进海豚，然后用自然语言描述需求生成对应的 XML。
2. 【要求】`template` 现在为颜色，后面可以做扩展，这版本不考虑。
3. 【要求】解析器对 Action 的统一处理逻辑还需补充细节 ✅（已在方案 3.2.2 补充六环）。
4. 【要求】模块化：以后如果允许最终用户（而非开发人员）编写，卡片定义可能不放代码而放数据库，设计需要考虑加入这一层不会影响核心代码。

## 第八部分 · 交付物清单

### 第一版产出 4 个文件
1. 【交付】`card.xsd`（词汇表规范）：XML Schema 形式带注释，定义 8 个元素及每个元素的字段和取值。
2. 【交付】`SKILL.md`（技能文档）：教海豚怎么用这套 DSL——词汇表、语义颜色规则、动作轮次规则、模板用法、示例。
3. 【交付】`feishu_card_render.py`（工具入口）：海豚实际调用的工具，传入 XML 或模板名，返回编译好的飞书卡片 JSON + 动作映射表。
4. 【交付】`_card_dsl.py`（渲染引擎实现）：XML 解析、合法性校验、编译成飞书 2.0/legacy 两种卡、语义颜色映射、Action 轮次生成与 handlers 预注册、回调 value 组装、模板加载与占位符填充（约 550 行）。

### 配套三件事

## 第九部分 · TODO 卡（feishu-todo-card）技能全部要求点

### 9.1 定位与根本区别
- 【设计】一张卡列多条待办，**逐条勾选**。普通卡片点一次整张退休；TODO 卡把"一次性"粒度从整张卡降到每一行。
- 【设计】每条待办一个勾选形状（○● / □■ / ◇◆ / △▲ / ☆★ / ☐☑）、一个详情链接、一个对应飞书任务。

### 9.2 工具选择
- 【要求】一张卡列多条待办逐条勾 → `feishu_todo_card_send`。
- 【要求】勾选后回调标飞书任务完成 → `feishu_todo_card_tick`（卡片自动派发，不用手调）。
- 【要求】一张卡只要一个答案（同意/驳回、选一项）→ `feishu_message_send_card`，**别用 TODO 卡**。
- 【要求】自己拼多选卡（非待办形状）→ `feishu_message_send_card` + `multi_use=True`。

### 9.3 标准流程
- 【要求】**先建飞书任务，再发卡。** 每行链接指向它自己的飞书任务，任务不存在就没有可点目标。
  1. 对每条待办 `POST /open-apis/task/v2/tasks`，拿回 `task_guid`。
  2. 组 `items_json`，把 `task_guid` 填进对应行。
  3. `feishu_todo_card_send(receive_id="ou_...", items_json=...)`。

### 9.4 每行可配字段
- 【设计】`title` — 待办文字（必填；空的会变成"任务 N"）。
- 【设计】`task_guid` — 对应飞书任务，渲染成 applink 链接。
- 【设计】`link` — 显式 URL，**覆盖** applink（想链到文档而非任务时用）。
- 【设计】`shape` — 该行形状：circle ○● / square □■ / diamond ◇◆ / triangle △▲ / star ☆★ / check ☐☑。不填用卡片级 `shape`。按任务类型区分形状靠这个字段。
- 【设计】`detail` — 标题下第二行（截止时间、验收标准）。
- 【设计】`done` — 预置已完成：渲染成删除线且不给按钮。
- 【设计】未完成 = 空心 + 加粗；已完成 = 实心 + 删除线 + 无按钮。

### 9.5 链接：applink 不是 web url
- 【要求】`task/v2` 返回体里没有 web URL 字段，别去等它。工具用官方客户端跳转协议拼：`https://applink.feishu.cn/client/todo/detail?guid=<task_guid>`。
- 【要求】要跳到别处（文档、多维表格记录）就填 `link` 覆盖。

### 9.6 幂等边界（会踩的地方）
- 【要求】**逐行 at-most-once，不是逐卡。** 勾第 1 行不影响第 2 行；重复勾第 1 行恰好被拒一次（跨进程、跨重启都有效，靠 per-action 墓碑文件）；并发同时勾两行也各自成立。
- 【要求】每行 `action` 必须唯一且规范（无前后空格）。工具自动生成 `todo_tick_<行号>`，自己拼卡务必照办——两行撞名会互相顶掉。
- 【要求】没有可用 action id 的行会退回整卡去重，即退化成普通单次卡：点一下整张卡就没了。
- 【要求】已勾状态会回写快照。否则第二次勾会从原始卡渲染，把第一行完成状态覆盖回未完成。日志出现 `failed to persist ticked card` 说明后续勾选会显示错行——重发一张新卡。

### 9.7 防重放两层机制
- 【设计】墓碑文件 `{message_id}.{action}.consumed`：挡同一行被重复消费（含飞书 at-least-once 重投、进程重启后重投），作用域跨进程/跨重启。
- 【设计】每卡一把 `anyio.Lock`（读-改-写临界区）：挡两行同时勾时交错覆盖彼此完成状态，作用域单进程内。
- 【设计】墓碑用 `Path.touch(exist_ok=False)`，CPython 上就是 `os.open(O_CREAT|O_EXCL|O_WRONLY)`，原子（`exist_ok=True` 才走非原子 utime 路径）。
- 【设计】锁只在单进程内有效，这是够的：一个飞书 app 只能有一条 WS 长连接消费者（飞书平台限制，非本项目选择；本机起两个实例会互相抢连接），所以同一张卡并发勾选必然落在同一进程。多进程分别收到同一卡回调时锁失效但墓碑仍成立——退化后果是"某行完成状态可能被另一进程回写覆盖"，不是重复执行动作。

### 9.8 其他硬性要求
- 【要求】**别用 `feishu_message_edit_card` 改 TODO 卡。** 它不重新注册回调，编辑后按钮全是死的。
- 【要求-连点合并】在途回合期间到达的点击全部并进下一个回合，按 `(message_id, 点击者)` 分键——群卡里两人各点各的，互不合并、各自回复。
- 【要求】合并后收到批量壳 `<feishu_card_action_batch count="N">`，**每条都要处理**（逐条调 `feishu_todo_card_tick`，一条不能漏——合并只省回复不省动作），但只回一条消息总结或 `NO_REPLY`。不要一条点击回一段话。
- 【要求】**不要用飞书原生 checker 组件**（Card 2.0）：框架只把 action/button/form 当交互元素，checker 不在其中，点了不被消费机制识别，一次性保证和"已完成"回显都不生效。用文本形状字符 + 按钮。
- 【设计-完成后流程】勾选 → 框架把该行改成 `● ~~文字~~` 并原地更新卡片 → 派发 `feishu_todo_card_tick` → `PATCH /open-apis/task/v2/tasks/:task_guid` 写 `completed_at`（毫秒）+ `update_fields`。
- 【要求】漏了 `update_fields` 飞书会返回成功但一个字段都不改。工具已带上，自己调 API 时注意。
- 【设计】行内没有 `task_guid` 时返回 `task_updated: false` 并说明原因——不是错误，只是没有任务可动。
- 【要求】卡片在勾选那一步已经更新好，不要再发一遍、不要复述点击动作；只有任务更新失败才需要回话。
- 【要求-权限】标任务完成默认走机器人 token。机器人不是任务成员时会被拒——传 `user_key`（点击者 open_id）以本人身份完成。
- 【要求-上限】单卡最多 40 条，超了先拆卡。行数多时飞书客户端会折叠，重要的放前面。

## 第十二部分 · 已修复的真 Bug 清单（工作区版，共 5 项 + 1 项结论修正）

- 【Bug-④报错消息误导】按钮缺 `action` 时先撞 `_resolve_handler` 报 "no handler"，盖住真正问题。修法：action-row 分支里先查 `action` 非空（`raise "<button> requires an action attribute"`）再 resolve；未知元素消息补上 `list`。

## 第十四部分 · 维持现状的优化点（逐条理由）

第二轮通读引擎 + 边界实测挖出若干可优化点，逐条调查后**全部维持现状**：

- 【维持-A1】`rounds` 属性引擎不读（硬编码 20）：若让 per-element 生效会破坏"全卡统一轮次"不变式（score 注册 5 轮、comment/button 仍 20 轮，重建 round+1 时 score 先越界丢 handler），有副作用。现状属性哑值恰好 =20，行为正确，作为"支持多轮改分"的自文档保留。（注：zip 修正版 E 已安全实现引擎真读 rounds，见第十三部分）
- 【维持-A2】同名 action 两组 score 的 `action_id` 撞车：非功能 bug。实测两组 `record_id` 正确区分（recA/recB）；`_review_card_impl` 落账/重建只读 `record_id`+`score` 不读 `action_id`（`_review_card_impl.py:197,207`）；飞书墓碑认回调 value 的 `action` 字段，点一次整轮全换名。`action_id` 是下游无人读的冗余字段，撞车不触发错误。
- 【维持-A3】`<info>` 的 value 未做 markdown 转义：全 workspace 既有约定。成熟 todo 卡（`_todo_card_impl.py:144`）同样把 title 直插 markdown 不转义；单独给 info 加转义会与 todo 卡不一致，且飞书 markdown 转义语义无官方保证，贸然转义可能显示多余反斜杠。若要修应全局统一，超出本次范围。
- 【维持-B/C 类】`done` 大小写、except 风格不齐、selected 复用 `_parse_round`、`column_set` 字面量重复、预注册三段式重复——均为低价值锦上添花，按"无必要不改"维持现状。
