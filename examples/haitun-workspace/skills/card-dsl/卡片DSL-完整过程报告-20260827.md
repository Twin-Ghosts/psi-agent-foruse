## 一、这套东西是什么 / 为什么做

海豚（集成在飞书里的 agent 产品）所有人机交互都落在飞书交互式卡片上。飞书卡片有几个协议坑：**按钮点一次就永久失效、输入框的值必须靠 confirm 才回传、部分组件不支持、文本里的引号会撑爆 JSON**。

卡片 DSL 让业务只写约 10 行 XML 声明「卡上有什么」（标题 / 信息行 / 打分 / 评语 / 按钮 / 待办列表），由**渲染引擎**编译成飞书那几百行 JSON，并统一填平上述协议坑。三层架构：

    XML DSL（原创声明语言，人/LLM 写）
      ↓ 渲染引擎（原创编译器，当前飞书后端，预留 HTML）
    飞书卡片 2.0 JSON（平台协议）
      ↓ 飞书客户端
    用户看到的卡片

出自黄子建方案《todo：交互界面通用元素-以卡片为例》，DDL 8.28。

### 第 5 轮：硬化对抗测试 + 我挖到的 2 个真 bug

- **rounds 死键**：`<score rounds="N">` 只注册 N 个 handler，但 `round_` 被独立钳到 `[0,19]`；当 rounds < round_+1（如模板 rounds=5 已重建到第 6 轮）会渲染出无 handler 的死按钮。修法：`depth = max(rounds, round_+1)`，当前轮永远可路由。

- 顺带探明：XXE / billion-laughs 被 Python 3.14 的 expat 挡在解析层（外部实体报错、放大因子超限拒绝）。

## 三、最硬的那个 bug：评价卡「轮次+1」（六环核心）

这是海豚对抗审查报告里最关键的发现，也是 final 版 5 项修复中的 P0，值得单独讲透。

### 症状
评价卡打了 3 分想改成 5 分时，**改分无反应**（静默失败）。

### 根因（推断链，逐环核实）
飞书按钮点一次就废，卡片「反复能点」靠轮次机制：每次重建，按钮动作名从 `review_score_r0` 换成 `r1`/`r2`……换新名来「复活」按钮。但评价卡这条断了：
1. `_render_review_card` 签名无 `round_` 参数，内部 `render_template` 不传轮次，恒渲染 round 0（注释却反复声称「every rebuild bumps a round」——注释与代码不符）。
2. 评价卡 `multi_use=True`；5 个分数按钮的 `value.action` **全是 `review_score_r0`**（仅 `action_id` 各异）。
3. Channel 去重键取 `value.action`，墓碑文件名 = `{message_id}.{action}.consumed`。
4. 于是：点任一分数 → 墓碑 `review_score_r0` 消费 → 重建仍 r0 → 再点（改分）命中已消费墓碑 → 被静默拦截。

### 修复（final 版 `5e50bd8`，最小改动、对齐设计意图）
- `_render_review_card` 新增 `round_: int = 0` 参数，透传 `render_template(round_=round_)`。
- 新增 `_round_of_value(value)`：从回调 `value["round"]` 读当前轮次，对 `bool` 做防御。
- 点分 / 评语 / 打回三处重建各传 `_round_of_value(value) + 1`；发卡路径不传，保持 r0。
- 配套：引擎 `depth = max(rounds, round_+1)`（我第 5 轮挖的死键修复）保证重建轮次超过模板声明 rounds 时当前轮 handler 仍注册。

### 证据（离线可跑，本机实测）
- 渲染轮次随入参递进：`round_=0→review_score_r0`、`=1→_r1`、`=2→_r2`，且每轮 handler 均已注册。
- `_test_review_round.py`（4 项）：改分回调携带 round 0 → 重建 `value.action=review_score_r1`；改分携带 round 1 → 重建 `_r2`。每次全新轮次，墓碑不再命中。

### final 版的追加增强（`2e622b7`）
- **轮次用尽终态**：round ≥ `_MAX_ROUNDS`(20) → `_compile_terminal` 只读终端卡（交互元素降级为纯文本、不发 action、handlers 为空），而非把轮次钳回 19 重发死键。对齐 todo 卡的 `locked` 终端态。
- **双 score action_id 去撞车**：`_score_columns` 加 `occurrence`，同 action 多组 score 也序号化。
- **新增 `_test_card_dsl_strict.py`**（46 项，零 stub 跑真实运行时）。

## 五、当前功能全貌（final 版）

- **词汇表 8 元素**：`card / info / score / comment / action-row / button / list / row`，XSD 带注释可喂海豚生成 XML，语义色映射（accept→蓝、reject→红、default→灰），业务只写语义不写颜色。
- **Action 六环**：声明 → 带轮次动作名 `{action}_r{round}` → 全轮预注册 handlers → 回调 value 组装/反解 → 状态重建（高亮/回填/轮次+1）→ 业务边界隔离。
- **轮次生命周期**：发卡 r0；每次重建 `_round_of_value+1` 绕开墓碑；轮次用尽 → 只读终端卡。
- **模板与数据库预留**：`review-card.xml` / `todo-card.xml` 两模板，发卡只填数据不写结构；引擎入口只吃 XML 字符串，卡片定义将来可从文件切到数据库，引擎零改动（Dustin 第 4 点）。

## 七、一个明确的判定：落账 91403 不是引擎 bug

实卡测试中评价卡打分/评语「落账」报 `91403 / RecordIdNotFound`。逐层核实：根因是**测试卡用了合成 `record_id`（rec_t111/rec_t112），台账里没这行**——不是引擎缺陷。真实链路（todo 卡 tick → 解析真实 `recXXX` 再发卡）不受影响。引擎坚持「记录缺失只上报、不静默建行」是**正确设计**（盲目 create 会把测试数据塞进他人真实台账、污染生产数据）。

可选增强（本轮经确认**暂不改**）：落账前先 `_fetch_ledger_row` 探测记录存在性，把「记录缺失」与「真落账错误」在返回值里分开上报。不改的原因：落账代码本机与自检机器人「12」都无法验证——机器人 12 的自检脚本（`feishu_longconn_test.py`）收到回调只打印 value + 弹 toast，从不调用落账/重建代码，落账那行在这条链路里一次都跑不到；真正验证需海豚一号完整运行时。
