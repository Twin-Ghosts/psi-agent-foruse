## 一、这套东西是什么 / 为什么做

海豚（飞书机器人）所有人机交互都落在飞书交互式卡片上。飞书卡片有几个协议坑：**按钮点一次就永久失效、输入框值靠 confirm 才回传、部分组件不支持、引号会撑爆 JSON**。

卡片 DSL 让业务只写 ~10 行 XML 声明「卡上有什么」（标题/信息/打分/评语/按钮），由**渲染引擎**编译成飞书那几百行 JSON 并统一填平这些坑。三层架构：**XML DSL（原创语言）→ 渲染引擎（原创编译器）→ 飞书卡片 JSON（渲染后端）**。

## 三、当前功能全貌（zip 版）

### 3.1 词汇表 8 元素
`card / info / score / comment / action-row / button / list / row`，XSD 带注释，语义色映射（accept→蓝、reject→红），业务只写语义不写颜色。

### 3.2 Action 六环（多轮交互核心）
声明 → 带轮次动作名 `{action}_r{round}` → 全轮预注册 handlers → 回调 value 组装/反解 → 状态重建（高亮/回填/轮次+1）→ 业务边界隔离。

### 3.3 轮次生命周期（zip 版关键增强）
- **发卡** round 0；**每次重建** `_round_of_value(value)+1`，动作名全新，绕开 multi_use 墓碑 `(message_id, value.action)`。
- **轮次用尽（round ≥ _MAX_ROUNDS=20）→ 只读终端卡** `_compile_terminal`：交互元素降级为纯文本信息行、不发 action、handlers 为空（而非把轮次钳回 19 重发已消费的死键）。对齐 todo 卡的 `locked` 终端态。

### 3.4 模板与数据库预留
`review-card.xml` / `todo-card.xml` 两模板，发卡只填数据不写结构；引擎入口只吃 XML 字符串，卡片定义将来可从文件切到数据库，引擎零改动。
