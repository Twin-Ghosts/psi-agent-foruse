## 一、问题（承认属实）

海豚对抗审查报告的发现 1、发现 2，我逐条去代码核实后确认**属实、非虚报**：

- **发现 1（轮次+1 未落地）**：`_render_review_card`（`_review_card_impl.py:571`）签名无 `round_` 参数，内部 `render_template("review-card", ...)` 不传轮次，恒渲染 round 0。三处重建调用点（点分 L226 / 评语 L325 / 打回 L507）全部没传轮次。而函数上方注释（L18-22、L176、L266）反复声称「every rebuild bumps a round counter」——**注释与代码不符**。
- **发现 2（改分被墓碑拦截）**：评价卡 `multi_use=True`（L703）。实测渲染发现 5 个分数按钮的 `value.action` **全部是 `review_score_r0`**（仅 `action_id` 各异 `review_score_1_r0`…`_5_r0`）。而 Channel 去重键取 `value.action`（`src/psi_agent/channel/feishu/_card_action.py:292-295`、`_action_id_of` L341-350），multi_use 墓碑文件名 = `{message_id}.{action}.consumed`（`handle_card_action` L418 传入的正是解析自 `value.action` 的 key）。
  - **推断链**：点任一分数 → 墓碑 `review_score_r0` 被消费 → 重建仍是 r0（发现 1）→ 再点任何分数（改分）命中已消费墓碑 → 被静默拦截。这正是六环「多轮改分」的核心卖点，却因轮次没加而失效。

### 更正对方两处不准确表述（不推翻结论）
1. **`_round_of` 不是全仓死代码**：`_review_card_impl.py:133` 的 `_round_of` 在评价卡内确实未被调用；但 todo 卡有**独立的** `_round_of`（`_todo_card_impl.py:93`），被 `feishu_todo_card_tick.py:86`、`feishu_todo_card_untick.py:61` 实际调用。轮次机制在 todo 卡是活的，只有评价卡这条断了。
2. **被测 HEAD**：报告抬头 `ca49c4c` 是纯 docs 提交，代码修复在其父 `283e730`。不影响结论。

## 二、修复（本轮改动）

### 改动文件
- `examples/haitun-workspace/tools/_review_card_impl.py`

### 改动内容
1. **`_render_review_card` 新增 `round_: int = 0` 参数**，透传给 `render_template(round_=round_)`。发卡路径（`_send_review_card`，L713 区）不传 → 保持 round 0；三处重建传 `当前轮次+1`。
2. **新增 `_round_of_value(value)` 辅助函数**：从回调 `value["round"]`（int，引擎在 `_base_value` 写入）读当前轮次，缺失时回退解析 `value["action"]`（`{action}_r{round}`）。对 `bool` 做了防御（`True` 不得被当成 round 1）。
3. **三处重建路径各加一行 `next_round = _round_of_value(value) + 1`，并传 `round_=next_round`**：
   - 点分 `_handle_score_select`（L189）
   - 评语 `_handle_review_input`（L279）
   - 打回 `_handle_review_reject`（L451）

### 为什么这样修（对齐设计意图，改动最小）
六环设计原意就是「轮次+1 → 全新 action 名 → 绕开墓碑」，注释早已写明，只是实现漏了。加 `round_` 参数是**实现设计意图的最小改动**，不动 Channel 去重逻辑（避免全局行为变更），不动引擎。

### 配套保障（工作区既有、非本轮）
`_card_dsl.py` 工作区已有一处加固 `depth = max(rounds, round_ + 1)`（`_compile` L317 区），保证「重建轮次超过模板声明 rounds」时当前轮 handler 仍注册、不成死键。此改动与本轮修复配套——见第四节高轮次证据。

## 三、有效性证据（本轮修复生效）

### 3.1 渲染轮次随入参递进（发卡 r0，重建递增）
```
round_=0 -> score action=review_score_r0 | handler registered=True
round_=1 -> score action=review_score_r1 | handler registered=True
round_=2 -> score action=review_score_r2 | handler registered=True
round_=3 -> score action=review_score_r3 | handler registered=True
```

### 3.2 改分场景闭环（驱动真实 handler，用假回调）
`_test_review_round.py::test_score_click_rebuilds_next_round`：
- 首次点分回调携带 round 0 → 重建卡 `value.action = review_score_r1` ✅
- 改分回调携带 round 1 → 重建卡 `value.action = review_score_r2` ✅
- 每次 action 名都是全新轮次 → **墓碑 `review_score_r{n}` 不再命中已消费项，改分放行**。

打回路径同理：`test_reject_click_rebuilds_next_round` 携带 round 2 → 重建 `review_score_r3` ✅。

### 3.3 高轮次不成死键（配合 depth 加固）
```
round_=5  -> review_score_r5  | handler registered=True (total handlers=60)
round_=7  -> review_score_r7  | handler registered=True (total handlers=60)
round_=19 -> review_score_r19 | handler registered=True (total handlers=60)
```

### 3.4 `_round_of_value` 取值正确
`test_round_of_value_reads_int_then_action`：`{"round":4}`→4、`{"round":"2"}`→2、`{"action":"review_score_r5"}`→5、`{"round":True}`→0（bool 防御）、`{}`→0，全部通过。
